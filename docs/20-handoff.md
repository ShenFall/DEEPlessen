> 2026-11-22 收尾。一个做功能，一个做视觉，共用同一个仓库。

## 0. 总工程师是谁

**功能侧（栈师）担任总工程师。** 不是因为它写得最多，而是因为它同时握着三样东西：数据模型、接口契约、构建是否通过。

| 职责 | 说明 |
|---|---|
| 接口契约 | `Screen` 的 props 由它定；加字段必须先过它 |
| 数据真相 | 哪个数字从哪张表来，由它说了算，不许前端编造 |
| 构建把关 | 合并前必须 `npm run build` 绿；红了它负责修或退回 |
| 提交权 | 只有它执行 git，避免半成品入库 |
| 技术裁决 | 选型分歧（如 R2 vs COS）它给方案，**你拍板** |

**它不管的三件事**：产品该做什么（你）、好看不好看（视觉侧）、什么时候上线（你）。

冲突升级规则：**碰到产品判断 → 你；碰到视觉偏好 → 视觉侧；碰到"数据对不对、会不会崩" → 总工。**

## 1. 分工（三方，不是两方）

| | 代码实现（我） | 图片设计（混元） | UI 交互设计（Kimi） |
|---|---|---|---|
| 产出 | 数据层、逻辑、构建、提交 | **位图**：壁纸、概念稿、图标草图 | **样式与组件**：CSS、布局、动效组件 |
| 目录 | `src/db` `src/fs` `src/storage` `src/lib` | `assets/`（只写，不删） | `src/ui/`、`src/features/*/*.css` |
| 不碰 | 视觉参数 | 代码、SVG、命名规范 | 数据调用、`db`/`fs`、提交 |
| 交接物 | 可运行的界面 + 数据契约 | PNG/JPG 文件 + 用途说明 | 纯展示组件（props 不含数据） |

**三方最容易打架的地方**：一张图到底是"生图"还是"用 SVG 画"。

判断规则：
- **要随主题变色、要缩放不失真、要能改一笔** → SVG/CSS，归 Kimi
- **照片、纹理、插画、壁纸** → 生图，归混元
- 加载器（轨道绘图）属于前者，**明确不生图**

**明确归代码侧的判断**：某个字段该不该显示、点了之后发生什么、失败了怎么提示。
**明确归 UI 侧的判断**：这块放哪、多大、什么颜色、有没有动效。
**明确归图片侧的判断**：壁纸画什么、什么质感、什么构图。

## 2. 接口契约（视觉侧可以自由改结构，但不能改这些 props）

```ts
DashboardScreen  { data, paidCounts, onOpen, onAll, onLibrary }
ReconcileScreen  { students, assignment, initialPaid,
                   onBack, onOpenImport, onToggleStatus, onClone }
AssignmentList   { assignments, paidCounts, onOpen,
                   onCreate, onUpdate, onDelete, onImportRoster, onToday }
LibraryScreen    { onBack }
ImportScreen     { onCancel, onDone }
```

需要新字段：**先跟功能侧说**，由功能侧加进 `db/index.ts` 的类型与查询函数，视觉侧再接。

## 3. 三条纪律（都是已经踩过的坑）

1. **提交只能由一方做。** 上次 `git add -A` 把另一路的文档、README 索引一起卷进提交，还误生成过一份 478 行的方案。
   现在：功能侧只 `git add` 自己改过的路径；视觉侧**只写文件，不执行 git 命令**。
2. **同一个文件不要两边同时改。** 尤其是 `features/*/XxxScreen.tsx`——它同时含结构和逻辑。
   视觉侧要动结构时，先只改 CSS；必须改 JSX 时，先在会话里说一句"我要动 DashboardScreen 的 JSX"。
3. **改完跑一次 `npm run build`。** 它同时跑 `tsc --noEmit` 和打包，红了说明契约破了，别等对方发现。

### SVG 动效（轨道加载器）归谁

**不归素材生成，也不是功能侧一个人做。**

| 角色 | 做什么 |
|---|---|
| 素材生图 | **不参与**。ADR-0011 明确要求加载器用 SVG + CSS 实现；生成图无法响应主题、尺寸、`prefers-reduced-motion`，也无法改一条路径 |
| 视觉侧 | 写组件本身：路径形状、节奏、缓动、颜色、静态降级帧。产出 `src/ui/OrbitLoader.tsx`，props 只有 `size` 和 `label`，**不依赖任何数据** |
| 功能侧 | 负责挂载与退出：接 `ready` 状态，**不为了展示动画人为延迟**，reduced-motion 下直接静态 |

一句话：**视觉决定「怎么动」，功能决定「什么时候动、什么时候停」。**

现有占位在 `App.tsx` 的加载分支（`deep:~$ 载入…`），视觉侧直接替换那一块即可。

## 4. 谁先做视觉，谁先做功能- 功能侧：不等待，按 `15-m3-plan.md` 继续推（对象存储 → 学生端）。
- 视觉侧：可以基于**现有真实数据**改样式，不要为了好看伪造字段。
- 交汇点：功能侧每加一个新界面，先给**能跑的最小版**，再交给视觉侧改造。**不要先画空壳**。
